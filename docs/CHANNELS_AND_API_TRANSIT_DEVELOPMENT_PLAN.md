## 1. 结论

当前项目可以接入这两个栏目，但不应把它们直接塞进现有的 `products`、`plans`、`sources` 或 `/api-pricing` 数据模型：

- **API 中转站栏目可行，建议优先做。** 它与本项目已有的模型目录、价格采集、采集运行记录、异常告警和 PostgreSQL 同步能力较接近。首版可只收录公开、可验证的站点和价格，模型检测服务不进入 MVP。
- **卡网比价栏目可行，但采集和治理成本更高。** 同一商品会出现大量店铺、库存、最低购买量、阶梯价、有效期和标题别名，需要独立的商品归一化、报价去重、商家审核、风险提示和公开读模型。
- 两个栏目都应作为新的领域边界实现，共享现有采集基础设施，但使用各自的规范化对象、数据库表和展示 API。
- 不得把 PriceAI 本身作为生产数据源，也不得复制其代码、数据集、渠道清单、页面文案或视觉资产。可借鉴公开可观察到的产品思路，实际数据必须从原始公开来源、授权接口或商家提交中独立取得。

本分支已完成**数据政策与 schema → 两个栏目只读 MVP → GitHub 快照采集通道**的基础闭环；真实来源白名单、生产 migration、数据导入和发布仍需按第 12 节决策及项目运维手册单独批准。后续顺序建议为：**获准来源接入 → 历史趋势与排名 → 独立模型检测服务（可选）**。

## 2. 调研范围与证据边界

本方案依据以下材料：

1. 两个公开页面及其在 2026-09-06 返回的服务端渲染数据和公开页面接口。
2. PriceAI 公开源码仓库中与栏目相关的路由、组件、数据库迁移和说明文档；仓库目前显示为 [`dimthink/PriceAI`](https://github.com/dimthink/PriceAI)，页面元数据中仍可见旧组织名。
3. 当前项目的架构、数据库 schema、采集器、同步逻辑及 [`COLLECTION_PROJECT_RUNBOOK.md`](./COLLECTION_PROJECT_RUNBOOK.md)、[`DATA_SOURCES.md`](./DATA_SOURCES.md)。

页面中的商品数、报价数、商家数、样本数和最低倍率会持续变化，调研时看到的数量只用于确认数据规模和接口行为，不应写入产品常量或验收标准。

### 2.1 合规边界

PriceAI 仓库采用 source-available 条款，并非可任意复用的开源许可证；其 [`LICENSE`](https://github.com/dimthink/PriceAI/blob/main/LICENSE) 对竞争性公开服务及商业使用有限制，[`DATA_LICENSE.md`](https://github.com/dimthink/PriceAI/blob/main/DATA_LICENSE.md) 也限制复制或镜像生产数据、渠道清单、价格快照、采集日志、分类结果和用户提交。

因此本项目必须采用 clean-room 原则：

- 只把公开页面行为作为需求参考，不复制对方实现代码、数据文件、页面内容、品牌或视觉资产。
- 不调用 PriceAI 页面接口作为本项目的线上数据源，不批量抓取或镜像其数据。
- 每个商家或中转站都从其原始公开页面、公开 API、授权 feed 或经审核的主动提交采集。
- 对 robots、服务条款、访问频率和数据再发布权逐源审查；不允许采集的来源不进入生产。
- 若未来确需改编其源码或数据，应先获得明确书面许可并完成法律审查。

## 3. 对方栏目如何工作

以下是从公开运行态与公开源码可以确认的产品和技术模式，不代表建议逐项照搬。

### 3.1 卡网比价 `/channels`

该栏目不是静态榜单，而是一条“多源报价 → 商品归一化 → 可用性判断 → 公开读模型 → 搜索/筛选页面”的数据链路。

#### 页面能力

页面分为三个视图：

- **标准商品**：把不同店铺标题映射为统一商品，展示最低可用价格、库存店铺数、异常标记和售后报价。
- **全部报价**：展示原始报价维度，包括店铺、标题、价格、币种、库存、最低购买量、阶梯价、标签、更新时间和链接。
- **卡网商家**：按商家聚合商品覆盖、在售数量、最低价/前五命中、有效比较覆盖、监测时间和风险反馈。

页面将查询条件同步到 URL，支持关键词、平台、商品类型、库存、价格范围、采集器、信号、视图和分页。首屏由 Next.js 服务端渲染，后续筛选和分页调用公开 JSON API；不会在页面请求期间临时抓取上游店铺。

#### 公开读模型

公开源码显示其为报价建立了独立的扁平读模型，预先合并商品、来源、库存、价格、有效期、搜索文本和刷新批次。刷新过程采用“生成新批次 → 完整性检查 → 原子切换/删除旧批次”的模式，并为搜索、平台、商品类型、可用性、价格、更新时间和来源建立索引。

这个设计解决了三个问题：

1. 页面查询不需要连接多张高频写入的采集表。
2. 某次采集返回空数据时，不会把上一批有效公开数据直接清空。
3. 搜索、筛选、排序和分页可以保持稳定、可复现。

#### 报价判定与去重

公开展示只把满足下列条件的报价视为“可参与最低价”：

- 有价格和目标链接；
- 未被标记为缺货、不可用、过期或采集失败；
- 有效期尚未结束；
- 同一公开去重键只保留优先级最高的记录。

去重优先考虑当前可用、非共享访问、来源优先级、分类置信度、更新时间和稳定 ID。商品榜单再按“有现货优先、最低价、稳定名称/ID”等确定性条件排序。

商家排行使用最低价命中、前五命中、有效比较覆盖、当前可用性等可解释指标，并声明商业合作不应改变自然排名。商家提交进入单独入口，不能直接变成公开记录。

### 3.2 API 中转站 `/api-transit`

该栏目采用“站点目录 + 分组/模型报价 + 可用性样本 + 来源与风险说明”的结构，而不是只保存一个倍率数字。

#### 页面能力

列表页支持关键词、模型、模型家族、渠道类型、账号池和排序筛选，主要展示：

- 站点名称、网址、系统类型、运营主体和状态；
- 充值倍率、模型倍率、站内分组倍率及综合倍率；
- 近七日成功率、样本量、延迟和最近检测时间；
- 渠道类型、账号池、付款/退款/发票信息；
- 来源、风险标签、数据状态和更新时间。

详情页按模型家族和分组展开输入、输出、缓存读写、图片输出或固定计费价格，同时展示监测范围、样本、来源证据、风险、优势和注意事项。

#### 倍率与计费

对 token 计费的报价，可使用以下统一展示量：

```text
充值因子 = 支付金额 / 充值到账计费额度（同币种）
综合倍率 = 充值因子 × 有效模型（或站内分组）倍率
```

例如“支付 1 元到账 10 元”对应充值因子 `0.10x`。固定次数、固定图片或媒体价格不能强行换算成文本 token 倍率，应以原币种和计费单位独立展示。

#### 可用性样本

可用性不是单一站点字段，而是带有以下维度的时间序列：

- 范围：站点、分组、模型或具体报价；
- 匹配级别：精确、分组回退、模型回退等；
- 来源：本站探测、公开状态页、公开模型目录、用户提交或未知；
- 指标：成功/失败、时间、延迟、近七日成功率和样本量。

展示时必须标明来源和覆盖范围，不能把某个模型的成功样本描述为全站稳定，也不能把第三方状态页数据包装为本站实测。

#### 数据来源适配

公开源码表明其数据源以配置化适配器接入，可读取站点公开 JSON、公开模型列表、公开状态页或人工审核快照。适配器按来源类型解析成统一站点和报价结构，再生成列表页数据。

#### 模型识别服务

“模型识别”是独立服务，不在主站进程内完成：用户提交 Base URL、临时 API Key、模型、协议和检测深度，主站把任务发送给隔离服务并轮询同源状态接口。页面要求登录，可结合 Turnstile，并建议使用低余额临时密钥。

这类功能涉及秘密处理、SSRF、上游调用费用、滥用、日志泄露和检测结论误导，不应纳入两个栏目的首个版本。

### 4.1 为什么不能直接复用现有价格表

现有 `NormalizedOffer` 表达的是“一个 provider 的一个 product/plan 在某区域和渠道的价格”。卡网的核心关系是“多个 merchant 同时销售同一个 canonical product”，而中转站是“一个 station 下有多个 group/model/channel/account-pool 组合”。把这些维度塞入现有字段会产生大量伪 provider、伪 product 和不可验证的字符串字段，也会污染当前官方价格榜单。

## 5. 建议架构

### 5.1 领域划分

```text
共享采集运行框架
├── 官方价格领域（现有）
├── 卡网领域
│   ├── 商家与来源
│   ├── 规范商品与别名
│   ├── 当前报价与历史观测
│   └── 公开读模型与商家统计
└── API 中转站领域
    ├── 站点与来源
    ├── 模型/分组报价
    ├── 可用性样本
    └── 公开读模型与风险说明
```

页面路由建议：

- `/channels`：标准商品、全部报价、商家三个视图；
- `/channels/merchants/[merchantSlug]`：商家详情，可在第二阶段增加；
- `/api-transit`：中转站列表；
- `/api-transit/[stationSlug]`：中转站详情；
- 保留 `/api-pricing` 作为模型官方价格目录，不改变其含义。

### 5.2 卡网数据模型

建议至少新增以下表：

#### `channel_merchants`

商家主数据：`id`、`slug`、`name`、`host`、`website_url`、`status`、`operator_type`、`platforms`、`risk_labels`、`first_observed_at`、`last_reviewed_at`。

#### `channel_sources`

商家的具体采集入口：`merchant_id`、`source_type`、`entry_url`、`collector_kind`、`terms_status`、`crawl_interval`、`enabled`、`last_success_at`、`consecutive_failures`。同一商家可有多个来源。

#### `channel_products` 与 `channel_product_aliases`

规范商品及别名：平台、产品类型、规格、展示名、别名、人工审核状态。分类规则必须版本化，并保存原始标题到规范商品的映射置信度。

#### `channel_offers`

当前报价：来源、规范商品、原始标题、价格、币种、库存状态、库存数、最低购买量、阶梯价、链接、有效期、标签、首次/最近发现时间、分类置信度和公开去重键。

#### `channel_offer_observations`

不可变历史观测：报价键、采集运行、价格、库存、有效期和观测时间。按月分区或设置保留策略，避免无限增长。

#### `channel_submissions`

用户/商家提交：网址、名称、联系方式、说明、审核状态、审核人和审核时间。联系方式属于非公开数据，不能进入公开同步或日志。

#### `channel_public_offers` 与 `channel_merchant_daily_metrics`

面向页面的扁平读模型和每日商家指标。读模型必须带 `generation_id`，只在新批次通过最小数量、字段完整性和异常波动检查后原子切换。

关键索引：

- `(canonical_product_id, availability_status, price_minor)`；
- `(merchant_id, last_seen_at desc)`；
- `(source_id, public_dedupe_key)` 唯一或部分唯一；
- 搜索文本的 trigram/全文索引；
- `(generation_id, platform, product_type)`；
- 历史观测按 `observed_at` 的 BRIN 或分区索引。

金额统一存最小货币单位或精确 decimal，不使用浮点数。阶梯价使用有 schema 校验的 JSON，待查询需求稳定后再拆表。

### 5.3 API 中转站数据模型

#### `transit_stations`

站点主数据：`id`、`slug`、`name`、`website_url`、`api_base_url`、`status`、`station_system`、`operator_type`、`invoice_support`、`commercial_relation`、`summary`、`risk_labels`、`data_status`、`last_reviewed_at`。

`commercial_relation` 必须与排序字段分离，页面显著披露赞助/返佣关系。

#### `transit_sources`

来源入口及证据：`station_id`、`source_type`、`source_url`、`collector_kind`、`authorization_status`、`enabled`、`last_success_at`、`last_error_at`。只允许公开、无登录或明确授权的来源。

#### `transit_offers`

当前模型/分组报价：

- 模型家族与规范模型 ID；
- 分组名、计费模式、币种；
- 充值因子、模型倍率、分组倍率；
- 输入、输出、缓存读写、图片输出或固定价格；
- 账号池、渠道类型、价格来源、验证时间和公开状态。

所有倍率使用 `numeric`，保留原始数值和推导后的综合倍率；综合倍率应由服务端按版本化规则计算，不能由前端各自解释。

#### `transit_offer_observations`

记录价格与倍率变化，保存 `collector_run_id`、原始响应哈希和观测时间，支持变更历史与回滚核查。

#### `transit_availability_samples`

字段至少包括：`station_id`、`scope`、`standard_model`、`group_name`、`offer_id`、`source_type`、`success`、`latency_ms`、`checked_at`、`failure_class`、`public_note`。只保存脱敏结果，不能保存 API Key、完整请求/响应或用户提示词。

#### `transit_submissions` 与 `transit_reviews`

分别保存站点提交和审核/风险反馈，全部默认 `pending_review`，经人工确认来源和证据后才能发布。

关键索引：

- `(station_id, status)`；
- `(station_id, standard_model, group_name)`；
- `(station_id, checked_at desc)`；
- `(scope, standard_model, group_name, checked_at desc)`；
- `(data_status, last_reviewed_at)`。

### 5.4 采集接口

共享的是执行框架，而不是领域返回值。建议新增两个接口：

```ts
interface ChannelSourceAdapter {
  collect(context: CollectionContext): Promise<NormalizedChannelOffer[]>;
}

interface TransitSourceAdapter {
  collect(context: CollectionContext): Promise<NormalizedTransitSnapshot>;
}
```

二者均复用现有 HTTP 客户端、超时、重试、内容哈希、运行记录、错误告警和幂等写入，但分别进行 schema 校验和数据库事务。不要把店铺库存或站点可用性塞入现有 `NormalizedOffer`。

每个来源配置必须包含：

- 来源所有者和公开入口；
- 服务条款/robots 审查结果及日期；
- 允许的请求频率、超时和最大响应体；
- 解析器版本、失败阈值、数据过期时间；
- 是否允许公开再展示、需要的来源署名；
- 关闭开关和维护人。

采集器必须限制重定向、域名、协议、DNS 解析、响应体大小和超时，以降低 SSRF 与资源耗尽风险。不得由用户提交的任意 URL 直接触发服务器抓取。

### 5.5 公开 API

建议提供本站自己的版本化接口：

```text
GET /api/v1/channels/products
GET /api/v1/channels/offers
GET /api/v1/channels/merchants
POST /api/v1/channels/submissions

GET /api/v1/transit/stations
GET /api/v1/transit/stations/:slug
GET /api/v1/transit/stations/:slug/history
POST /api/v1/transit/submissions
```

列表参数使用 Zod 白名单校验，限制 `limit` 上限，游标或确定性 offset 分页；响应包含 `generatedAt`、`dataStatus` 和降级说明。公开接口只查询已生成的读模型，不直接触发采集。

卡网 API 的 `limit` 最大 100、`offset` 最大 500,000，覆盖当前允许接收的全部报价；`total` 为当前视图的完整匹配数量，不是这一页的行数。报价、产品和商户详情与列表共享生成时间、代次、数据状态和安全降级提示。HTML 搜索词截取至 120 字符，输入框展示实际使用的值，不因超长搜索丢弃其他有效筛选。中转站内部审核模式的结构化筛选可匹配未发布报价，但公开 API 仍拒绝该开关。

数据库持续不可用时，最后可用快照仍按当前时间检查报价时效；超过 36 小时的商家报价健康状态与中转报价核验状态会降级，不因保存在内存中而无限延长有效期。

最后可用快照的监测证据超出七日窗口时清空可用率、样本数与样本展示；当前只接收站点级或精确报价级证据，组级、模型级或非精确报价级证据须待对应展示能力上线后再准入。卡网通用详情使用 `?kind=offer|product|merchant` 消除跨实体 ID 冲突，同类对象优先精确 ID 再匹配 slug；省略 kind 保留报价优先的兼容行为。报价独立详情只接受 offer 类型。价格升降序别名均可用，同价时先按来源健康状态、来源优先级，再按观察时间和 ID 排序。

监测聚合保留贡献样本的最早 `expiresAt`（滚动摘要使用该摘要到期时间），数据库故障期间也尊重显式到期，不必等待七日窗口结束。读模型样本数上限与整批最多 1,000,000 个原始样本一致，避免有效的大批量证据因较小的显示类型上限被丢弃。

### 5.6 公开读模型发布

每轮成功采集后执行：

1. 将规范化结果写入当前表和观测表；
2. 在数据库事务中构建新的 `generation_id`；
3. 校验记录量、必填字段、重复率、价格突变率和来源覆盖；
4. 通过后切换当前 generation；
5. 失败或异常清零时保留上一批，并把页面标记为延迟/降级；
6. 提交后再 revalidate 页面缓存。

这比在页面请求中实时聚合采集表更稳定，也避免上游短时失败直接清空前台数据。

## 6. 排名与展示规则

### 6.1 卡网

首版只提供可解释排序，不发布一个不可解释的总分。

- 商品最低价：只纳入已审核映射、在售、未过期、有价格、有链接且来源健康的报价。
- 同价排序：来源健康度、最近验证时间、商家名称和稳定 ID。
- 商家指标：最低价命中数、前五命中数、有效商品覆盖、当前在售数和数据新鲜度分别展示。
- 售后、共享账号、代充、成品号等商品形态应分开比较，不能只因标题相似混在一起。
- 赞助或返佣仅影响广告位及披露标签，不能改变自然结果。

### 6.2 API 中转站

- “最低倍率”只比较同一规范模型、相同计费模式和可比渠道。
- 样本不足时展示“样本不足”，不能把未知渲染为 100% 稳定。
- 近七日成功率必须同时展示样本量、来源和覆盖范围。
- 不同来源的数据不得静默合并为本站实测。
- 固定价格与 token 倍率分栏或分组展示。
- “综合推荐”首版建议由价格、公开监测、样本充分度、数据新鲜度和风险标记组成透明分项；算法版本、权重和更新时间均可追踪。

## 7. 数据可信度、审核与隐私

采用以下发布状态：

```text
submitted → pending_review → verified → published
                         ↘ rejected / suspended
```

- 商家/站点提交不会自动发布，也不会直接触发抓取。
- 原始标题映射、站点模型映射和风险标签都保存证据、置信度、规则版本及人工覆写记录。
- 页面区分“官方公开”“商家提交”“本站采集”“第三方状态”“用户反馈”，并链接到允许公开的来源。
- 联系方式、内部审核备注、访问令牌和探测密钥永不进入公开数据库快照。
- 对外链接按关系使用 `nofollow`、`ugc` 或 `sponsored`，并显示第三方购买和资金风险提示。
- 退款、发票、运营主体等信息只陈述可验证事实，不做资金安全背书。

## 8. 模型检测服务的安全门槛

若未来实施模型检测，应作为独立安全项目，至少满足：

- 与主站数据库和生产网络隔离的 worker/queue；
- API Key 仅存内存或带短 TTL 的加密队列，任务结束即销毁；
- 日志、异常、追踪和返回值统一脱敏，禁止记录 Authorization header；
- Base URL 经过协议、端口、DNS/IP、重定向和域名策略校验，阻断内网、metadata 和本机地址；
- 登录、Turnstile、单用户/单 IP 限速、并发和 token/金额预算；
- 明确支持协议，拒绝任意请求模板；
- 使用平台自有且获授权的测试密钥做持续探测，不依赖用户密钥形成公共评分；
- 检测结果描述为概率性信号，保留方法版本、误差和申诉入口；
- 完成威胁建模、渗透测试、隐私评审和成本上限演练后方可开放。

在这些条件具备前，页面最多提供站点公开信息和经授权的监测结果，不接受用户 API Key。

## 11. 验收标准

当前快照实现补充：导入入口再次校验运行时契约，文本、标签数量、阶梯价格结构及
单站报价上限与公开读模型一致；商家必须至少有一条 active 商家的 verified 报价，
中转快照必须至少有一个可公开站点，否则保留上一批数据。渠道详情 ID 按大小写精确
匹配；长来源 URL 仍完整保留，内部来源标识与去重标识使用稳定摘要，避免超过读模型
长度限制。旧 feed 的 `rechargeRatio: "1:2"` 可解析为 0.5；站点级可用性样本使用
`matchLevel: "station"`。这些约束均有单元或独立 PostgreSQL 往返回归测试。

读模型保留过期快照的 degraded 状态及提示；站点 ID 与 slug 分别去重。样本、产品
元数据和原站数量基线预先分组，避免按每个报价反复扫描完整数据集。详情路由与页面
元数据共享请求内加载结果，展示组件不再读取数据库。中转金额、倍率及计算结果必须
符合 numeric(20,8) 精度，正数低于 0.00000001 时拒绝发布，不能舍入成零价。

快照时间戳最多容许向未来偏差 5 分钟；渠道库存/起购量和最小货币单位金额不得超过
数据库存储范围。渠道来源健康度同时检查报价 lastSeenAt，超过 36 小时的旧观察不参与
最低价比较；列表各视图和总数共用先去重后筛选的集合。中转列表每站最多返回 5 条报价
预览，优先展示匹配筛选的报价，并返回 offerCount/ offersTruncated；完整价目在详情页。

结构化模型筛选后的站点排序仅使用匹配报价的价格、样本和核验时间，不让无关模型
影响结果；无核验时间的中转报价降为 unknown。降级状态在详情页首屏明确标注。
渠道过期/零库存证据优先于原始“有货”标签；混合币种不颁发全局最低价或前五名指标，
除非显式限定一个币种，产品卡片会说明不可跨币种比较。

### 数据与采集

- 每个公开字段可追溯到原始来源、采集运行和解析器版本。
- 相同输入重复采集幂等，不重复创建当前报价。
- 空响应、字段变化、超时和异常价格不会覆盖上一批健康读模型。
- 价格、币种、库存、有效期、倍率和模型映射均通过 Zod/数据库约束。
- 停用一个来源不会影响其他来源；可从后台执行下架和重新发布。

### API 与页面

- URL 筛选可分享、前进/后退可恢复，桌面和移动端均可用。
- SSR 首屏包含有效内容；筛选分页有稳定排序和上限。
- 页面明确显示更新时间、来源、数据状态、样本量和风险。
- 缺货/过期报价不参与最低价；不可比计费模式不混排。
- 商业关系不改变自然排名，且有清楚披露。

### 安全与隐私

- 提交接口具有限速、机器人防护、字段长度限制和审核队列。
- 任意用户 URL 不可触发内网访问或无限重定向。
- 联系方式、密钥、内部备注和完整探测响应不出现在日志、错误、缓存或公开同步中。

### 测试与发布门禁

实现代码必须按项目 `AGENTS.md` 完整执行分支、PR、CI、Codex 审核和生产发布流程；本地至少运行：

```text

npm run format:check
npm run lint
npm run typecheck
npm run test:coverage
npx next build --webpack
```

涉及筛选、分页、提交、详情跳转和错误降级时，增加并执行相应 Playwright E2E。采集器还需要 fixture、契约测试、清零保护、幂等和异常结构测试。

## 12. 开工前必须确定的产品决策

以下决策会改变法律风险、数据模型或运营成本，不能由实现者默认为“允许”：

1. 初始商家和中转站白名单，以及每个来源是否允许采集和公开再展示。
2. 是否接受返佣/赞助；如接受，其披露位置和与自然排序的隔离方式。
3. 用户反馈、商家申诉、下架和纠错的处理人及响应时限。
4. 可用性监测由公开状态页、平台自有测试账号还是合作方 feed 提供。
5. 是否未来接受用户临时 API Key 做模型检测；若是，必须另立安全项目评审。

## 13. 最终建议

**Go，但分两步进入。** 先建设 API 中转站的只读、可追溯版本，验证新领域表、来源准入和读模型发布流程；随后用少量获准来源建设卡网 MVP。两个栏目都应强调“信息比较与来源透明”，而不是对商家资金安全或中转服务真实性作背书。

首版应刻意不做：批量导入 PriceAI 数据、抓取 PriceAI API、自动发布用户提交、不透明综合排名、用户密钥模型识别，以及任何未经来源授权的规模化抓取。
